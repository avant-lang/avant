# Equivalence notes: Valk's general suite, tier 1, as shipped at Valk 0.8.5

One note per program, by the rule of D222: a row compares equivalent programs or it is labelled as not comparable, with the difference named. The three sources of each program were read side by side at tag `0.8.5` (commit `332243001c505373a8203cc60abaafcf188c4701`) of valk-lang/valk; file and line references are to `examples/bench/<program>/` there. Every count below was taken on this machine on 2026-11-12 with Valk 0.8.5, Go 1.26.0 (`GOEXPERIMENT=jsonv2`) and Rust 1.93.1, glibc 2.43; none depends on the clock. The raw files are in the record `results/2026-11-12-s29-wbench-suite/` (`raw/counts/`, `alloc/`, `regions/`, `profiles/`); the timings are in that record's tables, not here.

How each count was taken: instructions are `perf stat -e instructions:u`, one run, all threads of the process (Go's collector works on other threads, so Go's count is larger than its wall time suggests); Go's allocations are `runtime.MemStats` printed at the end of `main` by a scratch copy of each program (one `defer` line added), its collections `GODEBUG=gctrace=1` on the shipped binary; Rust's allocations are the calls of `malloc`, `calloc` and `realloc` counted by an `LD_PRELOAD` shim on the shipped binary; Valk's collections are `gc.gc.collect_count` printed by a scratch copy (one line added), its regions the compiler's `--region-report`, its object sizes the allocation calls in the IR (`--ir`). Valk gives no count of objects allocated, so Valk's object counts are the formulas from the source.

## Summary

| Program | Valk against Go | Valk against Rust | In one sentence |
| --- | --- | --- | --- |
| `binary-tree` | equivalent | equivalent, a weak baseline | The same 136,664,414 nodes of 16 bytes in all three; the row measures memory management: Valk's regions, Go's concurrent collector, Rust's `Box` per node on glibc's allocator. |
| `merkletrees` | **not comparable as shipped** | equivalent, a weak baseline | Go uses an interface with two node types and makes 1.50 times the allocations (102.3 M against 68.3 M) with leaves a third of the size; Rust and Valk use one 48-byte node type. |
| `lru` | **not comparable as shipped** | **not comparable as shipped** | Valk evicts with `HashMap.get_or_replace`, a library method added together with this benchmark, where Go and Rust do three plain map operations; the three linked lists also differ in kind. |
| `json` | equivalent as a task; library-leaning | equivalent as a task; library-leaning | Each language's dynamic JSON value, decoded and encoded 2,000,000 times; Valk's strings are views of the input where Go and Rust copy, and the output check is only a length. |
| `json-serde` | equivalent; library-leaning | equivalent; library-leaning | Typed decoding into the same four record types, with byte-identical encoded output (two MD5 sums); Go decodes by reflection, Valk and Rust by code generated at compile time. |
| `nsieve` | **not comparable as shipped** | **not comparable as shipped** | Valk's program is `@unsafe`: a raw array from `mem.alloc`, no bounds check, freed by hand; Go and Rust use checked arrays owned by the runtime. |
| `spectral-norm` | equivalent | equivalent | The same loops over checked arrays of 64-bit floats; Valk and Rust execute the same number of instructions to five digits. |
| `fannkuch-redux` | no Go program | **not comparable as shipped** | Valk's program is scalar and safe; Rust's is the SSSE3 shuffle program with `unsafe`; the program is in no runner and no published table of Valk's. |

Outputs: all eight programs print byte-identical output in every language that has the program and in every variant measured (58 rows; `raw/check/summary.tsv`). Valk's `run.sh` makes a difference between languages fatal only for `merkletrees` (`run.sh:251-254`) and a warning for the rest; this runner compares every run of every row with one expected file per program (`expected/`).

Build flags, the same for every program (from Valk's `run.sh:146-174`): Valk `valk build main.valk --release` (one whole-program LLVM module at O3; no `--cpu`, and the binaries contain no AVX or BMI instruction, so the baseline x86-64); Go `go build` (`GOAMD64=v1`; the runtime picks AVX paths for `memmove` and the like at run time by CPUID); Rust `cargo build --release` where the directory has a `Cargo.toml` (`lru`, `json`, `json-serde`: opt-level 3, no LTO, 16 code-generation units, the standard library precompiled) and otherwise `rustc -C opt-level=3 -C debuginfo=0` (target features `fxsr sse sse2` only). Nobody targets the native CPU. Labelled variants in the record: every compiler at x86-64-v3, and Rust with fat LTO and one code-generation unit.

## `binary-tree` (argument 19)

- **Output:** identical, ten lines.
- **Work done:** the same trees in the same order: a stretch tree of depth 20, a long-lived tree of depth 19, and for each depth 4, 6, …, 18 a loop of 2^(23−d) trees built, counted and dropped. By formula 136,664,414 nodes. Go's `Mallocs` is 136,664,760 (the nodes and 346 of the runtime's); Rust calls `malloc` 67,982,695 times and `calloc` 68,681,729 times, 136,664,424 together (the leaf `TreeNode { l: None, r: None }` is all zeros and is allocated zeroed, `main.rs:26`). The three check functions differ in shape and not in work: Valk reads both children and recurses when both are set (`main.valk:14-20`), Go tests the left child only (`main.go:22-27`), Rust tests each child (`main.rs:8-17`).
- **Memory management, which is what the row measures:** Valk's compiler puts every tree in a region with no hint in the source: `--region-report` gives `main.valk:7-10` (the nodes) "region of a caller", `:24` the stretch tree "region of stretch", `:38` the long-lived tree "region of main", `:46` the loop's trees "region of main, per round of a loop". The collector never runs (0 collections; 192 with `--no-regions`). Go allocates on its concurrent collector's heap (140 collections; 83.2 G instructions over all threads). Rust frees each node by a recursive drop into glibc's allocator: 58.2 G instructions, of which `_int_malloc`, `_int_free_merge_chunk`, `cfree`, `_int_free_maybe_trim`, `unlink_chunk` and `calloc` are more than half (`profiles/binary-tree-rust.txt`).
- **Safety:** the safe subset in all three.
- **Representation:** a node is two references, 16 bytes, in all three (Valk: `region_alloc(…, 16)` and the pool `ALC_16__Node` in the IR; Go: 2,187,040,568 bytes allocated over 136.7 M objects; Rust: 2,186,634,471 bytes requested, though glibc's smallest chunk is 32 bytes). Counters: Valk `uint` (64 bits), Go `int` (64 bits), Rust `i32` (`main.rs:8`; the largest value is 16,777,184).
- **Library:** none.
- **Verdict: equivalent** for Go. **Equivalent, a weak baseline** for Rust: the same program, with one `malloc` and one `free` per node where a Rust programmer who cared would use an arena; the row says more about glibc 2.43's allocator than about Rust.

## `merkletrees` (argument 18)

- **Output:** identical, ten lines (the one comparison Valk's `run.sh` makes fatal).
- **Work done:** by formula 68,332,206 nodes, of which 33,991,342 are inner nodes. Rust: 68,332,215 calls of `malloc`. Go: 102,323,907 `Mallocs`, which is the nodes plus one more object per inner node (102,323,548 by formula): `merged := …; n.hash = &merged` (`main.go:56-57`) puts each inner node's hash in its own 8-byte heap object, while a leaf's hash points into the leaf (`l.hash = &l.value`, `main.go:38`). Go therefore makes 1.50 times the allocations of the other two.
- **Representation:** Valk and Rust have one node type with two optional 64-bit integers and two optional children (`main.valk:1-5`, `main.rs:1-6`), 48 bytes (Valk: `region_alloc(…, 48)`, fields at offsets 0, 16, 32 and 40 in the IR; Rust: 3,279,949,735 bytes requested over 68.3 M objects). Go has an interface `INode` implemented by two types (`main.go:24-50`): a `Leaf` of 16 bytes and a `Node` of 40 bytes (a 48-byte size class) holding two 16-byte interface values, so Go's 2,453,383,408 bytes are 35.9 per node against 48. Every `CalHash`, `GetHash` and `Check` on a child in Go is a dynamic call through the interface (`main.go:54-56,63`); in Valk and Rust they are direct calls on one type.
- **Source tuned for one runtime:** Valk's loop body and its stretch tree are in `$noinline` functions, "Keep expired tree roots out of the next iteration's stack scan" (`main.valk:45-58`); Go and Rust have the same statements inline in `main` (`main.go:101-105`, `main.rs:102-106`). At 0.8.5 the wrapper is also what gives each loop tree its region ("region of tree_hash", `main.valk:47`).
- **Memory management:** Valk: every tree in a region, 0 collections (216 with `--no-regions`). Go: 148 collections. Rust: `Box` per node, the same allocator profile as `binary-tree` (`profiles/merkletrees-rust.txt`).
- **Safety:** the safe subset in all three. **Library:** none.
- **Verdict: not comparable as shipped** for Go (a different data structure: an interface and two node types, one more allocation per inner node, dynamic dispatch). **Equivalent, a weak baseline** for Rust, as in `binary-tree`. A levelled Go twin (one struct, the hash stored inline) is more than a few lines and is left to the Valk stage.

## `lru` (arguments 1000 and 11,000,000)

- **Output:** identical: 1,101,955 hits and 9,898,045 misses.
- **Work done:** every iteration is one `put` of a random key and one `get` of another, keys modulo 10,000 in a cache of 1,000 entries, so about nine `put`s in ten miss and evict. On such a `put` Valk makes **one** call, `this.entries.get_or_replace(key, node.key, node)` (`main.valk:45`): it hashes and probes the new key, probes and removes the old key, and appends the new entry with the hash it already has, without probing for the new key again (`lib/src/core/hashmap.valk:544-567`). Go makes **three** map operations, each hashing and probing: `c.keys[key]`, `delete(c.keys, …)`, `c.keys[key] = ele` (`main.go:50,57,59`). Rust makes **three**: `get_mut`, `remove`, `insert` (`main.rs:161,172,176`). A `get` is one lookup in all three.
- **A library method added with the benchmark:** `get_or_replace` came to Valk's library in commit `7dae2b32` ("adjust hashmap"), which changed `lib/src/core/hashmap.valk`, the tests and `examples/bench/lru/main.valk` together; before it, Valk's `put` was `get`, `remove`, `set`. It is a documented and tested method, and a reasonable one for fixed-size caches, but the row then measures the method.
- **The levelled twin** (`variants/lru-plain/main.valk`, the `put` Valk's own file had before `7dae2b32`): 7,261,521,201 instructions against the shipped program's 6,169,215,156, **+17.7%**. For scale, Go's shipped program is 8,683,895,182 and Rust's 6.1 G to 7.1 G depending on the run (below).
- **Representation:** the lists differ in kind. Valk: the list is in the node itself (`key`, `value`, `prev`, `next`, 24 bytes, `main.valk:1-6`) and the map goes from `u32` to the node. Go: `container/list`, whose element holds an `any`, here a `*Pair` (`main.go:16-18,64`), so two objects per entry and a type assertion on every access (`main.go:43,52,57,60,61`). Rust: `Rc<RefCell<LinkedListNode<(K, V)>>>` with `Weak` back-pointers and a map of `Weak` (`main.rs:9-10,132`), generic over the key and value with `Clone`; every access upgrades a weak reference and checks a borrow flag at run time, and moving a node to the end is a removal and an insertion with reference counts changed each time (`main.rs:69-96`). Keys and values are 32-bit in all three.
- **Library:** Valk's `HashMap` (grouped control bytes, dense entries, an integer mix as the hash, `hashmap.valk:157-183`), created with the capacity; Go's built-in map (`make(map[uint32]*list.Element, size)`); Rust's `hashbrown` 0.16.1 with its default hasher (`Cargo.toml:11`, `HashMap::with_capacity`).
- **Rust's work varies from run to run:** five runs of the same Rust binary executed 6.08 G, 6.28 G, 6.50 G, 6.78 G and 7.08 G instructions (`alloc/lru-instructions-per-run.txt`), because `hashbrown`'s default hasher (`foldhash` 0.2.0) takes a different seed in every process; Valk's five runs agree to seven digits (its integer hash has no seed) and Go's to 1%. Rust's row therefore has a wide spread in time that is the program's, not the machine's, and one instruction count of it means little.
- **Safety:** the safe subset in all three (Rust's `Rc<RefCell<…>>` is how the safe language writes a doubly linked list). **Allocation:** 1,000 entries and no collection anywhere (Go: 0 collections; Valk: 0).
- **Verdict: not comparable as shipped**, against both: a different number of map operations through a purpose-built method, and three different list representations. The twin measures the first difference; the second is each language "as normally written" and stays.

## `json` (argument 2,000,000)

- **Output:** identical: `Alice|30|alice@example.com` and `53`. The second line is only the **length** of the encoded text, so the encoders' outputs are not compared byte for byte by this program (Rust's map orders the keys, Go's map has no order).
- **Work done:** 2,000,000 decodes of one 53-byte object into the language's dynamic JSON value, then 2,000,000 encodes of the last value. Valk: `json.decode` into `json.Value`, where "the strings and keys without escapes in the result are views of `json` rather than copies" (`lib/src/json/parse.valk:56-57`), so a decode copies no text; 777 collections. Go: `json.Unmarshal` into `map[string]any` by reflection (`main.go:29-30`), the number becoming a `float64`; 30,001,354 `Mallocs`, 15 per decode and encode, 321 collections. Rust: `serde_json::from_str` into `serde_json::Value` (`main.rs:19`), whose object is a `BTreeMap` with the crate's default features; 14,000,009 calls of `malloc`, 7 per decode and encode (the map's node, three keys, two string values, the output buffer).
- **Library:** this row is the three libraries. Valk: `valk.json` of its standard library. Go: `encoding/json/v2` with default options, which Go 1.26.0 only builds with `GOEXPERIMENT=jsonv2` (Valk's README asks for Go 1.27 or later). Rust: `serde_json` 1.0.151, pinned by the `Cargo.lock` Valk ships for this one program (`json/Cargo.lock`).
- **Safety:** the benchmark code is in the safe subset in all three.
- **Verdict: equivalent as a task, library-leaning**: the same input, each language's dynamic JSON type, the same result read back. Valk's decoder does less work per decode by design (views instead of copies; the input must then stay alive), which is a real property of the library and is named beside the row. Go's count of instructions is five times the others' (42.7 G against 8.1 G and 8.2 G), spread over reflection and the collector (`profiles/json-go.txt`).

## `json-serde` (arguments `sample` and 50,000)

- **Output:** identical: two MD5 sums, of the encoding of one decoded document and of the encoding of an array of 50,000 decoded documents. The three encoders therefore emit byte-identical JSON, floats included.
- **Work done:** the 2,421-byte `sample.json` (one feature: a polygon of 14 coordinate pairs) is decoded 50,001 times into the same four record types (`main.valk:5-23`, `main.go:39-71`, `main.rs:4-29`), all 50,000 documents are kept in an array, and the array is encoded once. Valk: `json.decode_to[GeoData]`, generated at compile time; 23 collections. Go: reflection over struct tags; 1,800,650 `Mallocs`, 36 per document, 10 collections. Rust: serde's derived code; 1,050,041 calls of `malloc` and 100,027 of `realloc`, 21 and 2 per document (four strings, the three outer vectors and the 14 pairs).
- **Library and options:** Valk `valk.json` and `valk.crypto`'s MD5. Go `encoding/json/v2` (as above) and `crypto/md5`. Rust `serde` 1.0.229, `serde_json` 1.0.154 **with the feature `float_roundtrip`** (`Cargo.toml:14`), which is slower than the crate's default float parser and is what makes the MD5 match, `md5` 0.7.0, `anyhow`; this program ships no `Cargo.lock`, so these are the versions cargo resolved on 2026-11-12 (the lock file is in the record), and `serde_json` here is not the version `json` pins.
- **Representation:** Valk holds references to class objects (`Array[GeoData]`, `Array[Array[Array[float]]]`); Go and Rust hold the structs by value in slices and vectors. Floats are 64-bit in all three.
- **Reading the file:** Valk reads `sample.json` beside the source file (`__DIR__`, `main.valk:35`); Go and Rust read it from the working directory, so the runner starts every row in the program's directory, as Valk's `run.sh` does.
- **Safety:** the safe subset in all three.
- **Verdict: equivalent, library-leaning**, with `float_roundtrip` and the experimental `encoding/json/v2` stated beside the row.

## `nsieve` (argument 13)

- **Output:** identical, three lines.
- **Work done:** the same loops in all three: three sieves of 81,920,000, 40,960,000 and 20,480,000 flags, the inner loop from `2i` in steps of `i`, not bounded by the square root.
- **Safety, the difference:** Valk's function is `@unsafe` (`main.valk:4`): the flags are a raw `*[u8]` from `mem.alloc` (`:5`), indexed without a bounds check (`:12,16`) and freed by `defer mem.free` (`:6`). Go uses `make([]bool, n)` (`main.go:10`) and Rust `vec![true; n]` (`main.rs:4`): checked indexing, storage owned by the runtime.
- **Memory:** because Valk frees each array by hand and Rust drops each vector, their peak is the largest array; Go keeps the three arrays until a collection (143,690,232 bytes allocated, 1 collection), so Go's larger peak RSS in this row is the collector's laziness against a manual `free`, not a difference in the data.
- **The levelled twin** (`variants/nsieve-checked/main.valk`: `let flags = [u8]{ 1 x limit }`, the collector's storage with Valk's checked indexing): 3,544,994,171 instructions against the shipped program's 2,520,802,424, **+40.6%**; Go's shipped program is 3,248,577,705 and Rust's 4,308,607,814. In the twin Valk's storage comes from the collector, as Go's does.
- **Representation:** one byte per flag in all three; Go's flags are inverted (zero means prime, so the zeroed allocation needs no fill), Valk and Rust fill with ones.
- **Verdict: not comparable as shipped**: Valk's program is outside the safe language and manages the memory by hand. The twin is the comparable row.

## `spectral-norm` (argument 5500)

- **Output:** identical: `1.274224153`.
- **Work done:** ten rounds of two products, each product two passes of 5,500 × 5,500 divisions over arrays of 64-bit floats. Valk executes 19,062,739,609 instructions and Rust 19,062,506,577 (0.001% apart); Go 21,783,560,828.
- **A small difference, negligible:** Valk passes one temporary array to every product (`main.valk:38-41,70`); Go and Rust allocate a temporary per product (`main.go:39`, `main.rs:30`): 20 allocations of 44,000 bytes in the whole run (Rust: 21 calls of `calloc`; Go: 1,384,376 bytes allocated, no collection).
- **Safety:** checked slices in all three. **Representation:** indices are `uint`, `int` and `usize` (64 bits), elements `float`, `float64`, `f64`. **Library:** none (the square root and the formatting to nine decimals).
- **Verdict: equivalent.**

## `fannkuch-redux` (argument 11)

- **Output:** identical in Valk and Rust: `556355` and `Pfannkuchen(11) = 51`. There is no Go program.
- **Not in Valk's runner:** `run.sh` has neither the program nor an argument for it, and Valk publishes no number for it. This runner uses 11, the default in `main.valk:71` (Rust's default is 7, `main.rs:147`).
- **Work done:** Valk's program is the plain scalar algorithm over three fixed stack arrays `[uint x 16]` of 64-bit cells with checked inline indexing (`main.valk:2-4,31-43`). Rust's is a different program: the permutation is a `u128` shuffled with `_mm_shuffle_epi8` (SSSE3) and read with `_mm_extract_epi8` (SSE4.1), inside `unsafe` blocks with `transmute` and `get_unchecked` (`main.rs:27-33,56-63,67-73`), and the permutations are generated block by block (`main.rs:86-139`).
- **Build:** `rustc -C opt-level=3` targets the baseline CPU, where those intrinsics cannot be inlined into the callers; with `-C target-cpu=x86-64-v3` Rust's instructions fall from 7,571,555,666 to 3,489,848,595, while Valk's stay at 8.8 G (8,778,250,750 at the default, 8,854,770,115 at `--cpu x86-64-v3`).
- **Verdict: not comparable as shipped** (a different algorithm, vector intrinsics and `unsafe` in Rust; no Go). Valk's scalar program is the one an Avant port follows; Rust's row is shown for completeness only. Valk's cells are 64-bit; Avant's LangArena task `CLBG::Fannkuchredux` uses 32-bit cells (`research/valk/benchmarks.md` §6.2), which a port has to decide and state.
